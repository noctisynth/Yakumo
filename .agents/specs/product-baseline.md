# 产品与工程基线

文档编号：SPEC-001。状态：Active。更新：2026-10-14。
来源：本轮用户要求；FACT 系列为协议依据。这里的设计约束不是服务端逆向结论。

## 1. 已确定范围

项目中文名为“八云爱”，英文标识为 yakumo；命名来源见 README-001。

- 跨平台 Tauri 客户端，Rust 仅使用 stable 工具链。
- 支持登录、当前学校配置、记录及统计读取，形成生成与提交所需的数据链路。
- 用户在软件内生成跑步数据，预览并检查后提交到服务器，再核对记录及统计结果。
- 数据标记为合成来源；服务端判为有效不会将其改写为真实传感器采集。
- 不内置广告，不隐式发送与功能无关的数据；权限随实际功能申请。
- 当前已建立离线应用骨架；协议、账号和运动业务尚未移植。初始化范围见 SPEC-002。

首个兼容性证据来自 schoolCode=swpu 的学校服务。尚不能宣称其他学校兼容。
“跨平台”是交付目标；具体桌面和移动平台及优先顺序见 RFC-0001，未擅自承诺全部平台支持。

## 2. 前端工程约束

使用 React + Zustand + React Router + shadcn/ui + Tailwind CSS；业务代码采用 TypeScript。
前端样式必须使用 Tailwind CSS，布局、间距、颜色和交互状态尽可能通过工具类表达。
不为页面和业务组件创建原生 CSS 样式表；全局 CSS 只保留 Tailwind 入口、shadcn 主题变量及必要基础规则。
文件名使用 kebab-case，例如 run-preview.tsx、session-store.ts、run-record.ts。
组件及类型标识符仍使用 PascalCase，函数及变量按语言惯例使用 camelCase。
工具保留文件名不强制改名，Rust 模块命名遵循 Rust 惯例。

职责分组如下，表中的名称是逻辑目录类别，不引用任何现有本地路径。

| 类别 | 内容 |
|---|---|
| models | 领域数据类型、视图模型、校验结果；区分线协议 DTO 与界面类型 |
| components | 可复用组件；ui 子类别保留 shadcn 基础组件，业务组件在其外组合 |
| pages | 路由页面，组合功能；不直接实现密码学或构造 HTTP 请求 |
| stores | Zustand 状态及 action，不持久化访问令牌或密码 |
| hooks | React 复用行为和订阅逻辑 |
| services | 对 Tauri 命令的类型化调用及边界转换 |
| lib | 无业务副作用的工具及组件辅助函数 |
| routes | React Router 路由声明和导航边界 |
| styles | 主题和全局样式 |

shadcn 的组件生成别名须与 TypeScript 和构建工具一致。models、pages、kebab-case 是本项目
要求，不声称是 shadcn 对全部工程的强制标准。其组件配置机制见
[shadcn 官方配置文档](https://ui.shadcn.com/docs/components-json)。

## 3. Biome 契约

配置文件名为 biome.json。以下格式设置已在初始化阶段落地；实际配置还包含 lint、命名、导入和 CSS 规则。

```json
{
  "formatter": {
    "enabled": true,
    "indentStyle": "space",
    "indentWidth": 2
  },
  "javascript": {
    "formatter": {
      "quoteStyle": "single",
      "jsxQuoteStyle": "single"
    }
  }
}
```

JS、TS、JSX、TSX 采用单引号；JSON 仍按 JSON 语法使用双引号。Biome 负责前端格式和 lint；
类型检查仍单独执行。初始化时为实际安装版本匹配配置 Schema 和锁文件，不在上下文中猜测
最新版本。配置字段依据 [Biome 官方配置说明](https://biomejs.dev/reference/configuration/)。

## 4. Rust 与原生边界

stable 是工具链通道要求，不代表产品已经达到稳定发布质量。当前采用 Tauri 2；实际 Rust 与
依赖版本及验证结果见 CHECK-001。引入新依赖前继续验证 stable 兼容性。

网络、会话、签名、封包及敏感数据存储放在 Rust 边界；前端仅接收所需的脱敏视图与结果。
请求包装及签名使用同一个不可变会话快照和同一个时间戳，防止令牌刷新导致不一致。
生成器与纯协议转换不直接发送请求；应用层负责提交动作及结果核对。

Tauri 核心与 WebView 的边界及 capability 机制分别参考
[官方架构](https://v2.tauri.app/concept/architecture/)和
[官方权限说明](https://v2.tauri.app/security/capabilities/)。不默认暴露任意 URL、文件访问或 shell 能力。
不能仅因配置了 capability 就声称自定义命令的参数已得到完整业务校验。

## 5. 提交及结果语义

应用至少区分：草稿、检查失败、可提交、正在提交、结果待核对、已入库但无效、已判有效、
业务拒绝和传输失败。具体状态机为后续设计，但不得把这些情况折叠成单一“成功”。
服务端详情、列表和汇总若暂不一致，应呈现各自观察，不假定永远同步。

同一记录的提交意图应可追踪。连接超时或响应丢失后，不能通过自动重传猜测服务端是否已经
入库。identify 的服务端幂等性未知，本地互斥和持久化尝试标记不能被描述为远端恰好一次保证。
离线历史配置可以用于预览和测试，实际提交须绑定当前账号、当前配置与明确的提交意图。

## 6. 验收基线

- 协议移植具备独立的离线签名、封包、序列化与双层表单对照。
- 生成样本可复现，距离、时间、速度、步数及分桶相互一致；不将圆形轨迹称为道路匹配路线。
- UI 展示当前配置、生成参数、摘要及提交状态；异常响应有明确含义。
- 会话材料不出现在前端持久状态、公共夹具或日志；无未声明的第三方通信。
- 目标平台分别构建和验证；某一平台成功不代表整个矩阵完成。
- 真实服务验证使用当次授权账号和范围，记录接收、详情、列表及汇总；常规测试不自动上传。

精确的命令合同、依赖版本、地图方案、存储格式和平台矩阵尚未冻结，见 RFC-0001。
